## WHAT

`@tapflowio/flow-runner`: deterministic YAML flow engine — the replay half of Automation.
Flows are authored once (by an agent via MCP, or by hand) and replayed with **zero LLM calls**: same input → same execution, no API cost in CI.

Published on the standard npm channel and versioned by changesets in the repo-wide fixed group. Publish only via the changesets flow — see [CONTRIBUTING.md § Branches & releases](../../CONTRIBUTING.md#branches--releases).

Consumers: `tapflow flow run` (CLI) and the `run_flow` MCP tool — both drive the same engine, so results never diverge.

## HOW

- `schema.ts` — YAML → `Flow` (hand-rolled validation, indexed error messages `file: steps[i]: …`). Step vocabulary is deliberately minimal: `clearState / launchApp / tapOn / inputText / pressKey / swipe / scroll / openUrl / assertVisible / assertNotVisible / pressButton / longPressOn / pinch / setOrientation / setPosture`. The last five exist because Flow Capture can record only what a flow can say, and a person in the dashboard presses buttons, holds, pinches, turns and folds. `scroll { until }` and `pressKey { modifiers }` are there for the same reason: a captured swipe is replayed by what it brought on screen, since its distance is not reproducible (a fling's length depends on its release speed), and a captured key can be a chord. No fixed `sleep` step — waiting is always condition-based (`assertVisible` + `timeout`).
- **A point and a secret are their own step types**, under the YAML keys people already write: `tapOn: [x, y]` is `tapPoint`, `longPressOn` with a point is `longPressPoint`, `inputText: { secret: NAME }` is `inputSecret`. Widening `tapOn.selector` or `inputText.text` instead would have made every reader of those fields — `matchSelector`, `suggest`, the labels, the YAML writer — branch on a shape it never meant. A point is the last resort: it waits for nothing (`VISION.md`). **A secret's value is the caller's to give, never the environment's**: `EngineOptions.secrets` holds only what the CLI's `--secret NAME` flags read, `run_flow` passes none (an MCP server's environment holds its relay token, and an agent's flow must not be able to type it into a field it then reads), and a flow naming a secret it was not given is refused before its first step. Names and labels carry the name, never the value or its length.
- `engine.ts` — executes steps against the `FlowDriver` interface (DIP: relay transport, mcp adapter, and test fakes all satisfy it). Selector resolution: bare string → exact identifier → exact label → partial label → exact placeholder (last, so a selector that resolved before a field carried one resolves the same way; never partial); `{id}` / `{label}` are explicit, and `{label}` never reads a placeholder. **Multiple matches on `tapOn` fail immediately** (no implicit first-pick); `assertVisible` accepts ≥1. Polls `queryUITree` every 500ms up to the timeout (default 10s, per-selector `timeout` override). `launchApp` waits differently: until the tree's structure holds still for a second, capped 3 s after the first successful read — see `waitForScreen` for why a single read cannot tell a splash from the first screen.
- `suggest.ts` — on a `tapOn` that matched nothing or several, up to three replacement lines from the last tree the poll saw (B2), no LLM. **Each is written out, read back through `parseSelector` and must tap exactly that element** (identity, not "one match": a bare string resolves by identifier first, and iOS identifiers often equal another element's title); `index` is the last resort; an `input` is offered by its `id` (with `role`/`index` when ids repeat) or its placeholder, never its label, since the label can be what was typed and a placeholder never is. **Never for `assertVisible`**: a near match there is as often the app being wrong, and an agent reading `get_run` would apply it and turn a regression green.
- `platformCheck.ts` — **a flow pressing a button the device lacks is refused before it runs**, never answered with a press that did nothing (the iOS agent acks `back` as success by #484 — right for an agent that looks again, wrong for a flow that cannot). Two layers, one function: the CLI and `run_flow` call `unavailableButton` with the platform before a device is chosen (the build's, or `--parallel`'s `--platform`), which refuses what a platform never has; the engine calls it again before the first step with the device's chrome (`EngineOptions.platform`, `FlowDriver.chrome`), for iOS buttons that exist only when the chrome declares them with a HID usage. The tables live in `@tapflowio/protocol/buttons` and both agents read them, so a name refused here is one the agent would not have pressed. A refusal is `failureKind: 'environment'` with `failedBeforeRun`, and a `--parallel` worker keeps its device after one — nothing reached the device, so the device is not suspect. A platform with no table is never refused.
- **A gesture this client opened is closed when it leaves the session** (`SessionChannel.openGestures`). Nothing on the relay or the agent lifts a pointer its client left down, and a long press or a pinch is open for its whole length, so a cancel lands inside one. A touch is closed with `input:touch:cancel` and then `input:touch:end`, so the app sees no tap or long press where the agent cancels and the gesture still completes where it does not (#1115); a pinch is only ended.
- `sessionChannel.ts` / `SocketFlowDriver.ts` / `browser.ts` — **the session semantics are split from the transport so a browser runs the same code** (Flow Capture verifies a flow in the dashboard, #1125). `SessionChannel` holds the waiters, the relay's word on each session, and what each input is on the wire (a swipe's eight moves, the gesture a leave closes, the ack an input waits for); a host subclasses it with `send` and feeds inbound frames to `dispatch`. `SocketFlowDriver` is the `FlowDriver` over any `SessionDevice` — a channel plus the tree and screenshot reads. `RelayClient extends SessionChannel` over `ws` and REST, and `RelayDriver` is `SocketFlowDriver` over it. `./browser` exports these with the engine, and `scripts/__tests__/flowRunnerBrowserGraph.test.mjs` walks its imports, across workspace packages, for a Node builtin, `ws`, a Node global or a secure-context-only API — which is why value imports of agent-core's errors come from `@tapflowio/agent-core/errors`, never its index (that reaches `downloadBuild`). Request ids come from `getRandomValues`: `crypto.randomUUID` is absent on a LAN dashboard served over http.
- `capture/` — **Flow Capture's judgement, as pure functions** (#1125): the relay's record of what a person did (`@tapflowio/protocol/capture`) turned into a flow. `segment` groups the record into actions; `defaultRange` picks where a flow starts (the first launch after the last install or clear-state); `replayStep` sends an action again on the person's session (gestures and keys as recorded through `SessionChannel.replayInputs`, so a recogniser reads the same spacing; launches, installs and pastes through the channel's own requests, so an install is fresh even when the viewer had asked to keep the app); `matchStep` turns an action into a step against the tree the host read just before replaying it; `toFlowSteps` and `flowToYaml` finish the file. The dashboard does the I/O; none of it is here, and it all ships in `./browser`. The rules that are easy to undo:
  - **A flow begins with a launch, and a range may not.** The dashboard's install does not launch the app; only its Launch button does, and measured on both platforms a person opened the sample app from its home-screen icon instead. So a range starts right after the last install when no launch follows it, `rangeWarnings` says `no-launch-at-start`, the flow gets a `launchApp` of its own (`CapturedFlow.launchAdded`, `flowSteps`), and the replay launches the app first. The icon tap is left for the person to cut by moving the start: telling the home screen from the app needs a fact the tree does not carry.
  - **Caps Lock is state, not a step**: folded into the typing it changes (a refused press changes nothing), kept as a key only when nothing was typed after it. Measured on iOS, toggled mid-field.
  - **Typing is cut at every key that types no character**, at any other input and at a 10 s pause (2 s cut a measured password in two), and each piece is judged by the field focused before it and, when one is, after it. A single run across a Tab would have put a password under the email field's verdict.
  - **Typed text is written down only into a field known not to hide it** — `secure: false` on the field focused before it, and on the one focused after it if any. Anything else (`secure: true`, absent, no focused field) is a secret: `PASSWORD` when the field says it hides its text, `SECRET` when it could not say. The values go back to the dialog for verifying, never into the file.
  - **A selector only when tapping its centre taps what the person did**: the hit element's centre is hit-tested again, and a selector comes from `suggest`'s verified forms (`selectorFor`), never from a secure element's label. Otherwise the point, marked fragile.
  - **A point is placed against the screen read at replay, not the recorded chrome**, which lags a turn by up to 3.6 s: an iOS point (the portrait framebuffer) by the tree's `interfaceTurn`, an Android body-mode point (`space: 'frame'`) by the settled `streamRotation`, any other Android point as it is.
  - **The end of a gesture is its last move** — the dashboard's `touch:end` carries no point, which is why the relay's thinning keeps that move.
  - **A swipe becomes `scroll { until }` only when it brought the tapped element on screen** and could be the engine's own swipe (straight, across the middle). A pager swiped to a page whose button every page has stays a swipe and a tap.
  - **Replayed only what replays the same way**: a key the device refused is neither typed nor sent again (a refusal can be transient and would land), the keyboard toggle and a network switch are not replayed, and a cancel stops before the next step and inside a recorded pause. A turn may be relative, so the host first restores `rangeStartOrientation`.
  - **Not exported, with a reason** (`SkipReason`): a refused input, a drag after a hold, a held button, a paste Android cannot type (`input text` takes printable ASCII), an install (the run installs and resets), a network switch, a cut, the keyboard toggle.
- `RelayClient.ts` / `RelayDriver.ts` — WS (session/input, message shapes shared with dashboard/mcp) + REST (`/ui-tree`, `/screenshot`). **A ui-tree failure is judged by what this client knows about the session before it is judged by the HTTP status**: a `terminated` session can never answer again and a rebound one cannot answer *this run* — the engine has no boot step to restore the binding — so those fail the step now and name the cause, while `away` — the relay's 15s hold — keeps polling, which is what the retry is for. Failing rather than recovering is what *same input → same execution* requires: a run that repaired itself by re-booting mid-flow would not be the same execution as one that did not, and the engine has no boot step to repair it with. `launchApp` targets the CLI `--build` / `run_flow` `buildId`, so flow files never hardcode a buildId and stay portable across CI runs.
- `inboundDisposition.ts` — what this client does with each message a browser socket can receive, or why it deliberately does not. A deliberate **copy** of `mcp-server`'s rather than a shared module: the key set is shared already (it comes from `@tapflowio/protocol` through `satisfies`), and the values genuinely differ — this package never shuts a device down, and its input-ack wrapper deliberately appends no session note where the other appends one. Checked both ways by `scripts/__tests__/clientInboundDisposition.test.mjs`.
- **A session-scoped failure carries what the relay said about that session**, through `failed()`, and `scripts/__tests__/sessionNoteCoverage.test.mjs` enforces it across both clients — see [mcp-server/AGENTS.md](../mcp-server/AGENTS.md) for why it anchors on the construction rather than the `throw`.
- `video.ts` — `VideoTap` turns the held stream into one video per flow (A4): records `[u8 kind][u32 BE ms][u32 BE len][payload]` (a frame as received, or a JSON event: chrome, device info, step marks from the engine's `onStep`), chunked at ~2 s / ~2 MB and before every decodable keyframe. **A chunk's `keyframe` means an IDR carrying SPS/PPS** — a point decoding can begin from. iOS and the emulator's gRPC encoder carry them on every IDR; scrcpy only on its first, so its video plays from the start and seeks only there. That is the backend's standing, absorbed rather than detected: protocol has no backend field, and a frame-based verdict could only arrive after the video was opened. A video starts at the last decodable keyframe before its flow, because a still screen may not key for a minute. JPEG is not kept, and a flow whose H.264 never offered a decodable keyframe (scrcpy after its first one has aged out of the 6 MB lead-in) opens with `notRecorded: 'no-keyframe'` so the page can say why rather than show nothing. The tap reads frames only through `RelayClient.setStreamListener`; the engine never sees it.
- `credentials.ts` — where a client's token comes from (T1): `--token`, then a non-empty `TAPFLOW_TOKEN`, then `~/.config/tapflow/credentials.json` (`$XDG_CONFIG_HOME`, `TAPFLOW_TOKEN_FILE`), keyed by relay origin with loopback hosts folded together. Here because mcp-server and cli both depend on this package and on neither other. **Opt-in**: `RelayClient` takes `string | TokenSource`, and a string is used as given — constructing a client never reads a file under `$HOME`, so a third party's token is never swapped for one it did not pass. `fetchWithToken` retries a 401 once **when the token differs from the one the request carried**, not from the last read, so every request in flight on an old token recovers; an explicit token is never replaced. Every relay 401 comes from its auth middleware before any handler, so retrying a POST is safe. `tokenRefusal` is the one message: which relay, which source, which fix.
- `eligibility.ts` — **whether a flow runs is decided in `isEligible` and nowhere else** (L1), for the CLI and `run_flow` alike: tag filter first (include is any-of, exclude wins, as Maestro), then `appId` against the build's bundle id. A flow carries no build; only a run is tied to one, so a future condition (a version range) is another field on the target, not a second place that decides. `lookupBuild` reads the bundle id from `GET /api/v1/builds/:id` and **treats only 404 as an answer**: that route wants `builds:write` while `flow run` needs only `view` and MCP may hold no token, so a refusal, a timeout or a null bundle id leaves the app check out instead of failing a run that works today. A skipped flow is not a `FlowResult` — the engine never saw it.
- `junit.ts` — one `<testcase>` per flow, step log in `system-out` / `<failure>`; a skipped flow (second argument) is a `<testcase>` with `<skipped>`, counted in the suite's `skipped`. `toJUnitXmlSuites` (a `--parallel` run) writes a suite per device, skipped flows in a suite of their own, and flows no device ran as `<error>` — never `<skipped>`, which CI reports show as green. `toJUnitXml`'s output must stay byte-identical: CI parsers already read it.
- `schema/tapflow-flow.schema.json` — JSON Schema shipped for editor autocomplete; keep it in sync with `schema.ts` when the vocabulary changes.
- Exit-code contract (CLI): `0` all passed · `1` any product or mixed flow failure · `2` environment/config error, including relay/agent/session failures when every failed flow is environmental. Never conflate 1 and 2 — CI dashboards rely on the distinction.
- Coordinates are normalized 0-1 everywhere and measured on the screen as the app draws it, matching the UI tree's frames. The touch path takes the device's portrait framebuffer, so `SocketFlowDriver` turns every point by the tree response's `interfaceTurn` (`@tapflowio/protocol/screen`); iOS reports it, Android's tree and touch already share one space. A step with no selector uses the turn of the last tree read, and `setOrientation` re-reads until two reads agree.
- `clearState` maps to `app:clear-state` (relay) → `pm clear` (Android) / data-container wipe (iOS `SimctlWrapper.clearAppData`).

## HOW NOT

- Do not call an LLM anywhere in this package — replay must stay deterministic and free.
- Do not add a fixed-sleep step; add condition-based waits instead.
- Do not resolve ambiguous selectors implicitly (first-match). Fail loudly with candidates.
- Do not put relay-side logic here — this is a client, like mcp-server.
- Do not let the engine depend on `RelayClient` — engine code touches only `FlowDriver`.
